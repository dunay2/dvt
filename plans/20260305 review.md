05DVT+ — Architectural Review
Basis: codebase examination across all packages, 32 ADRs, contract definitions, engine implementation, and gap tracker.

1. Conceptual Soundness
   What is solid
   The four-layer principle — UI doesn't execute, Engine doesn't decide, Planner doesn't persist — is enforceable at the contract level. The evidence:

IWorkflowEngine contains no planning logic. It accepts a PlanRef (reference, not content) and a RunContext. The engine is a dispatcher, not a reasoner.
IExecutionPlanner.buildPlan() returns only { plan, canonicalPlanJson } — it produces artifacts, it doesn't store them or trigger execution.
IRunStateStore is append-only. There is no update or delete on events. This is correctly modeled.
IProviderAdapter is correctly isolated. The discriminated EngineRunRef union per provider is the right pattern — each provider's run identity is fundamentally different.
Event sourcing with runSeq (monotonic integer) + idempotencyKey is the correct foundation for a deterministic execution system. These two fields together make deduplication and ordering verifiable.
StartRunIntentPolicy in the contracts layer (not in the adapter) with canTransitionStartRunIntent and getAllowedFromStatuses is a correctly-placed domain policy object.
What is fragile
stepTypeConfig: Record<string, unknown> is the largest architectural risk in the system.

The ExecutionStepV2 carries an opaque blob. The planner writes it, the adapter reads it, the engine never inspects it. This creates an invisible bilateral contract between planner and adapter that bypasses the type system, the ADR process, and all validation layers. When Conductor is added, the Temporal-trained adapter team will assume stepTypeConfig follows Temporal's serialization conventions. Conductor's activity dispatch model is different. Silent behavioral divergence is certain.

StepKind = string defers validation to execution time.

There is no step type registry. The planner can emit any string as kind. The engine will schedule it. The workflow activity will fail at runtime when it encounters an unknown kind. Validation of plan correctness requires executing the plan. This is not a deterministic execution system for unknown step kinds — it is a crash-at-runtime system with a deterministic replay journal.

Plan storage is undefined in the contracts.

PlanRef.uri assumes plans are stored somewhere accessible. IPlanResolver exists in the engine's port directory but has no visible implementation in the reviewed code. This is a structural hole: the Planner produces a plan, the Engine receives a reference to it, but the service that bridges producer to consumer is not specified. This means the Planner-to-Engine boundary is, in practice, held together by an unspecified S3 bucket or filesystem convention.

getSnapshot() replay model will not survive scale.

SnapshotProjector replays the full event log per call. For runs with 1000+ steps, this is O(events) per UI request. There is no async snapshot materialization. The current model is correct for small runs; it is architectural debt for large dbt projects.

EngineRunRef as a closed discriminated union is not extensible.

Adding a fourth provider (e.g., Prefect) requires changing the union type in @dvt/contracts, which is a breaking change for every consumer of the type. A registry-based design (provider: string; ref: unknown) would be more extensible, at the cost of type safety at the adapter boundary.

What is missing
No plan cycle detection — who validates that dependsOn in GraphNode[] is acyclic? The planner presumably does this but there is no contract-level guarantee. If a caller submits a plan with a cycle, the engine will deadlock.
No backpressure mechanism — a tenant can submit unlimited concurrent startRun calls. All become PENDING intents. No quota enforcement at the engine or planner level.
No plugin isolation contract — the product definition mentions plugins. No IPluginHost, no capability sandbox, no execution boundary is defined in the reviewed code.

Is IWorkflowEngine minimal and correct?

Mostly. Five methods: startRun, cancelRun, getRunStatus, enrichRunStatus, signal. The contract is intentionally narrow.

However: enrichRunStatus vs getRunStatus is a leaky distinction. getRunStatus reads local state; enrichRunStatus calls the adapter. Callers must know which to invoke in which context. This is not a clean abstraction — it exposes implementation details (local vs. remote read) at the interface level. Rename: getLocalRunStatus() and fetchAdapterRunStatus(). The names make the I/O implication explicit.

Is signal specified?

No. RETRY_STEP has an optional stepId. What happens if stepId is absent for a RETRY_STEP signal? Who validates this? There is no contract-level invariant. This is a latent source of ambiguous behavior across adapters.

Is Temporal-first wise?

Yes. Temporal's event-sourced replay model is a natural match for DVT+'s domain design. The risk is that Temporal's programming model bleeds into ExecutionPlanV2 through stepTypeConfig. If the planner starts embedding Temporal-specific hints (e.g., task queue routing, child workflow policies) in stepTypeConfig, then the "engine-agnostic plan" fiction breaks.

Is Conductor parity realistic?

No, not at behavioral parity. Temporal's deterministic replay and durable timers have no direct equivalent in Conductor. Conductor uses polling workers with server-side orchestration. The key differences:

Conductor has no local replay determinism guarantee — restarting a worker does not replay previous decisions.
Conductor's signal equivalent (wait tasks) is not composable the same way.
lookupRunRef is feasible in Conductor (workflow search by external ID), but idempotency guarantees for startRun are weaker.
Conductor will require behavioral shims at the adapter level that either accept reduced guarantees or add significant complexity. The current adapter interface design does not make these tradeoffs explicit.

Where determinism assumptions break:

Activities that read external state at execution time that was not part of the plan (e.g., dbt target schema fetched from environment at activity runtime, not from PlannerEnvironmentContext).
stepTypeConfig containing non-deterministic values (timestamps, random seeds) embedded by the planner — if an activity reads these and Temporal replays the decision, the values must be identical.
Any use of Date.now() or Math.random() outside the injected IClock/random boundaries. 4. Execution Planning Layer
DAG validation: The planner receives GraphNode[] with dependsOn from the caller. There is no visible cycle detection contract. If the caller submits a cyclic graph, the behavior is undefined.

Partial execution: PlannerSelection with includeUpstream/includeDownstream is correct in principle. The risk: a partial run that succeeds may leave Snowflake in a state where some downstream models are stale relative to updated upstream models. DVT+ has no mechanism to enforce consistency of the warehouse state post-partial execution. This is explicitly outside DVT+'s domain, but it should be documented as a known limitation for operators.

Retry ownership: PlannerPolicies.retries is defined at the planner level. Temporal handles retries natively at the activity level. There is a risk of double-counting retries if both DVT+'s domain retry logic and Temporal's activity retry policy are active simultaneously. Who wins? No resolution policy is defined.

Cost estimator: Not present in reviewed contracts. Mentioned in product definition as aspirational. Do not build this before the execution layer is stable.

Plan versioning: planVersion: '2.3' is a static string constant in ExecutionPlanV2. No version negotiation, no migration transform. When 2.4 is needed, every consumer must be simultaneously updated. This is a non-starter at scale.

Is the layer over-engineered? No, for the current scope. The planner is appropriately abstracted for a dbt+Snowflake execution system. The risk is complexity growth as stepTypeConfig accumulates step-type-specific fields without a registry.

Is it under-specified? Yes, in two ways: (1) no plan storage service definition, (2) no cycle detection contract.

5. State & Metadata Layer
   Is Postgres sufficient?

For the current scale, yes. At 1000+ tenants with thousands of concurrent runs:

run_events needs partitioning by (tenant_id, created_at) or (run_id) to avoid full-table scans in listEvents.
listRuns with a status filter requires a compound index on (tenant_id, status). Presumably present but not verified.
Write contention on appendAndEnqueueTx (events + outbox in one transaction) is the primary bottleneck under load.
Write amplification:

Every step completion writes: (1) event to run_events, (2) outbox entry to outbox_events, (3) snapshot update (when materialized). For a 1000-step dbt project: 1000 × 3 = 3000 writes per run. At 1000 concurrent runs: 3 million writes. Postgres can handle this with proper tuning, but the current shared connection pool is not sized for this.

Event sourcing vs snapshot tradeoff:

The system correctly separates the write model (append-only events) from the read model (snapshots). But snapshot generation is currently synchronous on read. This is the most important infrastructure gap to close before production.

Lineage snapshotting:

compiledCodeRef in S3 is architecturally correct for keeping the event log lightweight. The hard constraint (S3 outage at plan-build time = permanent lineage gap) is too high a risk for V0. The fix is simple: store SQL inline in StepStarted.payload with a 64KB cap. Migrate to S3-backed references in V1 once the execution layer is stable.

6. Plugin System
   Assessment: Not evaluable. No isolation strategy, no capability contract, no execution boundary is defined in the reviewed code. The product definition references plugins; the implementation has none. This is correctly deferred.

The risk of premature plugin design is higher than the risk of delayed plugin design. Do not architect this until the core execution path handles Temporal at production scale.

7. What Is Overbuilt
   IStartRunIntentCommandStore/IStartRunIntentQueryStore split at 6 methods total. The CQRS interface split adds complexity without benefit at this scale. IStartRunIntentStore with 6 methods is an appropriate interface. The split is architectural theater.

StartRunIntentSchemaManager with versioned migrations is well-engineered and functionally correct, but it re-implements Flyway's core loop (version tracking table, advisory lock, BEGIN/COMMIT per version). This creates a maintenance burden: two migration systems if the project later adopts Flyway/Liquibase for the rest of the schema.

compiledCodeRef (ADR-0032) at V0 scope — the S3 dependency, 4 parallel implementation tasks, and Evidence Doc process for what is essentially "capture the SQL that ran" is disproportionate to the risk it addresses. The traceability gap it solves is real, but the S3 failure mode it introduces (permanent lineage loss) is worse than the problem it solves at this stage.

reconcileOrphanedIntents PENDING path with lookupRunRef — this code path handles a crash between adapter.startRun() returning and markDispatched() being called, which is a valid case. But calling adapter.lookupRunRef() for every PENDING orphaned intent makes an external Temporal API call in the reconciler loop. This is an external dependency in a background job. A single Temporal API slowdown will block the entire reconciliation sweep.

8. What Is Underbuilt
   Missing or insufficient:

IPlanStorage — plan serving is not specified. The PlanRef.uri convention is an implicit contract.

Contract version negotiation — IRunStateStore.v1.ts has no version at the protocol level, only in the filename. If a breaking change is needed, there is no protocol for simultaneous old-and-new deployment.

Rollback guarantees — startRun has crash consistency via intents (ADR-0030). cancelRun, signal, and step dispatch have no equivalent crash recovery. A partial cancelRun that fails after RunCancelRequested is emitted but before the adapter is called is not recovered automatically.

Run retention policy — the event log is append-only and grows indefinitely. No TTL, no archival, no tenant-level quota.

Outbox ordering at multi-instance scale — ADR-0009 defines the invariant but neither proposed option is implemented. The OutboxWorker at single-instance scale is acceptable for development; it is incorrect for production.

StepKind registry — without a registry, plan validation requires execution. This contradicts the "engine does not decide" principle: if the engine must execute to discover the plan is invalid, it has taken a decision.

Temporal circuit breaker — if the Temporal server is unavailable, startRun will throw. There is no circuit breaker, no graceful degradation, and no visibility into Temporal server health in the engine's startup path.

Tenant-level concurrency limits — no quota enforcement for simultaneous runs per tenant.

detectStuckCancellingRuns CANCELLING substatus denormalization — CANCELLING is computed by reading the snapshot. This requires replaying events. Denormalizing cancelling_since to RunMetadata would eliminate the N+1 entirely.

DAG cycle detection contract — no explicit validation that the planner's graph is acyclic before emitting a plan.

9. Scalability Outlook — 3-Year Horizon
   1000+ tenants, thousands of concurrent runs, 1000+ node dbt projects:

run_events table growth: At 1000 tenants × 50 concurrent runs × 100 steps × 3 events = 15M events per complete cycle. Without partitioning by (tenant_id, created_at range) or run_id, listEvents degrades to table scans. Row count reaches billions within 18 months at this throughput.

OutboxWorker bottleneck: The outbox is a single shared table. Without per-tenant partition routing (ADR-0009 Option A) or row-level locking (Option B), the outbox becomes a serialization point. At 1000 tenants with burst activity, the outbox tail latency dominates event delivery time.

getSnapshot() replay cost: 1000-step runs with ~3000 events per run. If 100 users have dashboards open polling at 5-second intervals, that is 100 × 3000 = 300K rows read per polling cycle. This is not survivable without snapshot materialization.

Planner computation at 1000-node DAGs: Topological sort on 1000 nodes is O(V+E) — fast. The bottleneck is not compute but I/O: fetching the dbt manifest (potentially megabytes) and validating node references. The DbtManifestRef (URI + SHA256) approach is correct; manifest caching at the planner level is required.

Single points of failure:

getPgPool singleton — pool exhaustion in one component (OutboxWorker floods the pool) blocks all others.
Temporal server — no circuit breaker, no health check in startRun path.
S3 (post-ADR-0032) — plan fetch failures and compiledCodeRef failures both depend on S3. 10. Architectural Scorecard

Strategic Recommendations
3 structural changes

1. Materialize WorkflowSnapshot asynchronously.
   Add a workflow_snapshots table. After each appendAndEnqueueTx, enqueue a snapshot update job. getSnapshot() reads from the materialized table, not from event replay. This changes getSnapshot() from O(events) to O(1). This is non-negotiable before production at any meaningful run size.

2. Define and implement IPlanStorage as an explicit service.
   The Planner-to-Engine boundary currently relies on an unspecified URI convention. Define IPlanStorage with store(plan: ExecutionPlanV2): Promise<PlanRef> and fetch(ref: PlanRef): Promise<ExecutionPlanV2>. Implement a FilesystemPlanStorage for dev and S3PlanStorage for production. This closes the structural hole in the planner-engine pipeline.

3. Define a StepKindRegistry with validation at plan submission.
   StepKind = string must be replaced with a validated registry. The registry maps step kind → supported adapters + stepTypeConfig schema (JSON Schema or zod). Validate the plan against the registry at buildPlan() time, not at activity dispatch time. This converts runtime failures into submission-time failures.

3 clarifications needed

1. Who detects plan cycles?
   The IExecutionPlanner contract does not specify whether cycle detection is the planner's responsibility or the caller's. Define it explicitly in the interface. If it is the planner's, add a CyclicDependencyError to the contract.

2. What is the multi-instance outbox guarantee?
   Is it acceptable to have two OutboxWorker instances processing the same tenant's events? If yes, what ordering guarantee degrades to? If no, what locking mechanism is used? ADR-0009 defines two options but does not specify which is implemented and when.

3. What is the engineAttemptId semantics for Conductor?
   Temporal's retry model increments attempt count in the workflow. Conductor's retry model is server-side. The engineAttemptId: 1 hardcode in buildRunEvent is only correct for the first attempt. Define the attempt semantics in the event contract so both adapters can produce consistent lineage.

3 things to freeze immediately

1. IRunStateStore.v1.ts event type set — RunQueued, RunStarted, RunFailed, etc. Any new event type or payload field change must go through ARC-2 Evidence Doc with backward compatibility analysis. Changing event shape invalidates all stored event replays.

2. idempotencyKey generation in IdempotencyKeyBuilder — the key formula (eventType + runId + logicalAttemptId + planId + planVersion) is baked into stored events. If the formula changes, in-flight runs that were created with the old formula will fail deduplication checks.

3. EngineRunRef fields per provider — adding or removing fields from any provider variant breaks deserialization of stored refs in engine_run_ref JSONB in the intent store and in the event log.

3 things to delay

1. compiledCodeRef / ADR-0032 implementation — the S3 outage = permanent lineage gap is too high a risk for V0. Store SQL inline in StepStarted.payload capped at 64KB. Plan the S3-backed approach for V1 when the execution layer is stable and the operational team has S3 reliability controls in place.

2. Conductor adapter — full Conductor parity requires behavioral shims for determinism, retry semantics, and signal handling that Conductor does not natively support. Build this after Temporal achieves stable production operation with real integration tests passing.

3. Plugin system — no isolation strategy defined. VM2 is deprecated. Worker thread sandboxing requires significant infrastructure. Implement this after G1–G4 are closed and the core execution path has proven stability in a staging environment.
