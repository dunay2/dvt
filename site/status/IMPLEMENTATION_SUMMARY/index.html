    Type-drift strategy review (2026-02-19 18:37 UTC)¶

    Context: packages/@dvt/adapter-postgres/src/types.ts currently defines local transactional adapter types while the package also depends on @dvt/contracts.

    Evaluated strategies:

    1. Direct import/alias from @dvt/contracts now
    2. Pros: single source of truth for shared names.
    3. Cons: current exported contracts in packages/@dvt/contracts/src/types/state-store.ts model canonical event projection (appendEvent, fetchEvents, snapshots), not transactional outbox persistence (appendEventsTx, appendAndEnqueueTx, claim/delivery lifecycle).

    4. Risk: forced casts and semantic mismatch.

    5. Keep fully local adapter types (current state)

    6. Pros: clean separation and no false coupling.

    7. Cons: long-term drift risk on overlapping fields (eventType, RunMetadata, envelope shape).

    8. Introduce a dedicated shared transactional contract module (recommended)

    9. Add a new contract surface in @dvt/contracts specifically for transactional state-store + outbox behavior.
    10. Adapter and engine import from that module while canonical snapshot/projection contracts stay separate.
    11. Preserves decoupling-by-boundary while eliminating duplicated type definitions.

    Decision at this timestamp:

    • Keep local types for now.
    • Plan a follow-up to extract transactional shared contracts into @dvt/contracts and migrate packages/@dvt/adapter-postgres/src/types.ts and engine call sites together in one compatibility slice.
