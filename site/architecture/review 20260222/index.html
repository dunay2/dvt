    DVT+ Architectural Review Role: Principal Software Architect

    Date: 2026-02-22

    Sources: ADRs 0003–0016, IMPLEMENTATION_ROADMAP_FROM_REVIEW.md, WorkflowEngine.ts, @dvt/ packages, v2 architecture diagram, planning docs

    1. Conceptual Soundness The core thesis — domain-owned execution semantics over adapter-agnostic infrastructure — is architecturally correct. The insight that "Temporal's internal state is not the source of truth; the event log is" is the most important decision in the system. Any design that derives business state from a workflow engine's internal APIs ends up coupled to that engine permanently. DVT+ avoids this.

    The three-tier mantra (planner / engine / state) maps cleanly to three responsibilities:

    Planner: what to execute and in what order Engine: when to execute and what the lifecycle transitions are State: that it happened, immutably The problem is that only one tier is real. The planner doesn't exist as implemented code. The state store is a stub. The engine is implemented and architecturally sound, but it's a bridge to infrastructure that isn't there yet.

    The ADR process is a genuine strength. Twenty-six ADRs with explicit acceptance criteria, status boards, and traceability is not normal for a pre-production system. Most teams write ADRs post-incident. This one wrote them upfront and used them as implementation guides — the IMPLEMENTATION_ROADMAP_FROM_REVIEW.md demonstrates this directly, finding 7 active bugs by comparing ADR text to code. That's architecture as a tool, not decoration.

    There is a concept drift problem. Some documents describe DVT+ as a "dbt orchestration platform." Others describe a "generic deterministic workflow engine." The v2 architecture diagram shows React Flow canvas, diff views, lineage views, Snowflake cost attribution, a plugin system with sandbox execution, GraphQL API, and git sync — that's not a workflow engine, it's a platform product with 3+ years of scope. The conceptual model shifts depending on which document you're reading. This is not an engine architecture flaw. It is a product scope problem that will generate architectural pressure and mis-prioritization over time.

    1. getRunStatus is not a pure read model. getRunStatus calls adapter.getRunStatus() with a 30-second timeout. ADR-0015 is unambiguous: "The default read path MUST NOT call the provider." In multi-replica deployments, the in-process circuitStateByProvider map is useless — each replica holds independent circuit state. A Temporal worker restart causes 30-second latency spikes in every status query across every replica.

    2. The circuit breaker pattern is wrong by design. circuitStateByProvider: Map inside WorkflowEngine is process-local. It provides false safety in any deployment beyond a single Node.js instance. Circuit breakers must be shared state — Redis, or an external circuit breaker service. This component needs to be removed from the engine and replaced with infrastructure-level protection.

    3. capabilities validation is disabled. requiresCapabilities throws if capabilities.length > 0. Any plan that declares capabilities (which is the correct thing to do) will fail at runtime before an adapter is reached. This means the capabilities field in the plan schema is currently a runtime landmine.

    Third, retry policy in the plan schema is defined but enforced by nothing. RetryBackoffPolicy exists as a field. No component reads it and applies it during step failure handling. The roadmap correctly specifies hardcoded 3-retry policy for Phase 1, but that decision should be in a document, not implicit in code. 5. State & Metadata Layer Review

    Append-only run_events as source of truth Monotonic run_seq per runId Snapshot as optimistic cache for O(1) reads Outbox pattern for reliable at-least-once delivery to the event bus bootstrapRunTx as single atomic start point (now includes provider refs)

    1. No PostgresStateStore. The only persistence is whatever in-memory implementation exists for tests. DVT+ cannot be deployed. There is no Phase 1 MVP without this.

    2. Snapshot write-through is not implemented (W0-7). After each appendAndEnqueueTx, the snapshot is not updated. Every getRunStatus call requires full event replay via listEvents. For a dbt run with 1000 nodes, this is 2000+ rows fetched per status query. Under production load, listEvents will be the top-1 query by cost in the database.

    3. Plugin System Evaluation The plugin system does not exist. What exists: a box in the v2 architecture diagram, a note in the roadmap that vm2 should not be used, and references to IPluginRuntime as a planned interface.

    The recommendation to eliminate vm2 is correct. vm2 has documented sandbox escape vulnerabilities. It is not safe for production execution of user-provided code regardless of how carefully it is configured. The alternatives — worker_threads with strict IPC, V8 isolates (Deno-style), or container-per-plugin — are all more complex than vm2 for a reason. Secure plugin execution is genuinely hard.

    The plugin system as described in the v2 architecture (manifest, sandbox runtime, API surface, custom plugin types) is 6–12 months of engineering work post-engine-stability. The correct decision is in the roadmap: do not start the plugin system until IExecutionPlanner and IProviderAdapter are stable and in production. Building the extension surface before the product is validated is how systems end up with elaborate plugin infrastructure and no working core.

    The specific concern: if plugins can invoke adapter methods or access run state, the plugin API surface must be designed alongside those interfaces. A plugin API designed before IProviderAdapter is stable will either be too narrow (forcing breaking changes later) or too broad (creating a security boundary that's impossible to enforce). 7. What Is Overbuilt?

    1. Architecture diagram scope. The v2 diagram includes React Flow canvas, Snowflake cost attribution, plugin sandbox, diff view, lineage view, GraphQL API, and git sync. This is a 3-5 year product roadmap drawn as if it were current architecture. Aspirational diagrams in early-stage systems mislead planning by creating a false picture of completeness.

    2. ADR volume for unbuilt components. ADR-0002 (Neo4j as knowledge graph repository) and ADR-0006 (contract tooling governance) describe infrastructure with no code in the repository. Writing ADRs for hypothetical components produces documentation debt, not decision clarity. ADRs should follow implemented decisions, not precede unimplemented ones.

    3. @dvt/traceability-service package. This directory exists. The traceability infrastructure it represents (Neo4j, graph model, query surface) is completely unbuilt. Premature package definition without implementation creates dead code that accumulates maintenance surface.

    4. What Is Underbuilt?

    5. TemporalAdapter (real, not stub). Second critical path item. Nothing executes without it.

    6. Stuck-run detection. No mechanism exists to detect or recover from runs stranded in QUEUED. In production, a Temporal worker restart will orphan queued runs silently.

    7. Multi-tenancy enforcement depth. Tenant isolation is one missing WHERE clause away from a data breach. No Row Level Security in Postgres. No audit log of access patterns. No per-tenant connection isolation.

    8. Recovery procedures. What happens when Postgres is unavailable mid-transaction? When Temporal's cluster is unreachable for 30 minutes? When bootstrapRunTx partially commits? No documented recovery procedure exists. This is not optional for a system that positions itself as "reliable execution for critical workflows."

    9. Scalability Outlook (3-Year Horizon)

    Append-only event log partitioned by tenant_id + time scales to millions of runs with correct indexing. Snapshot write-through (W0-7 when implemented) decouples read latency from event log size. Adapter-first pattern means adding Conductor or BullMQ is additive, not disruptive to the engine.

    In-process circuit breaker. Doesn't scale past one replica. Has to be removed.

    listEvents without pagination. Unbounded. For a run with 1000 steps and 2000 events, this is megabytes per status query at production call rates. Projection recomputation without snapshots. Without snapshot write-through, every getRunStatus call triggers a full event replay. At 10 status queries per second per run across 100 concurrent runs = 1000 listEvents queries/second. With 2000 events per run, that's 2 million rows/second just for status queries.

    If plugins enter production under the worker_threads model, the horizontal scaling limit is roughly 500 concurrent plugin invocations per Node.js process before thread pool saturation.

    1. Architectural Scorecard Dimension Score Assessment Operational Readiness 2/10 No stuck-run detection, no pagination, no retention policy, no recovery playbook, no dashboards. Security Posture 4/10 IAuthorizer exists. Tenant isolation is WHERE-clause only. No RLS. vm2 risk documented not eliminated. Scalability Design 6/10 Correct patterns (event sourcing, adapters, outbox). runSeq contention and circuit breaker are concrete gaps.

    2. Implement W0-6 (getRunStatus read-path separation) as part of PostgresStateStore work. The read path must serve from the event log only. Separate enrichRunStatus if provider enrichment is needed for specific use cases. Remove circuitStateByProvider from the engine. Put circuit breaking in infrastructure.

    3. Eliminate vm2 from all planning documents and code comments now, not when the plugin system starts. The moment vm2 appears in a code file, it will be used. Specify the secure alternative — worker_threads with strict IPC message validation, or container-per-plugin — before any plugin execution code is written.

    • getRunStatus MUST NOT call adapter on default path (ADR-0015) — NOT YET DONE
