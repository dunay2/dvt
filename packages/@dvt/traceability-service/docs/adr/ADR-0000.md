# ADR-0000: Code Generation with Enforced Normative Traceability (Automated)

- **Status:** Accepted
- **Date:** 2026-02-14
- **Updated:** 2026-02-21
- **Owners:** Core Architecture / Engine / Adapters / AI Tooling

## 1. Context

Architectural drift is inevitable unless decisions are explicit, traceable, machine-verifiable, and continuously validated.

Traditional ADRs document intent but do not enforce conformance. This leads to orphaned code, silent violations, undetected architectural erosion, compliance ambiguity, and refactoring fragility.

### References

- C4 Model: https://c4model.com/
- Architectural erosion: https://www.oreilly.com/library/view/software-architecture-in/9781492086888/
- Technical Debt: https://martinfowler.com/bliki/TechnicalDebt.html

## 2. Problem Statement

We require a mechanism that:

1. Binds implementation artifacts to accepted ADRs
2. Survives refactoring and file movement
3. Is machine-verifiable in CI
4. Supports impact analysis
5. Generates an architecture dependency graph
6. Detects both code-without-ADR and ADR-without-implementation

This system must not rely on manual discipline alone.

## 3. Scope

Applies to: Core modules, Planner, Engine, Contracts, Adapters, Security modules, Public API, persistent models, generated schemas.

Does **not** apply to: pure UI presentational components, styling, internal utilities without architectural meaning, tests unrelated to architectural decisions.

## 4. Decision

### 4.1 Mandatory In-Code Traceability Header (Normative)

Every governed artifact MUST begin with:

```ts
/**
 * @file <path>
 * @baseline ADR-0010: <title>
 * @decision Section 3.3 — <decision text>
 * @consequence <system guarantee>
 * @version <semver>
 * @date <YYYY-MM-DD>
 */
```

Rules:

- Multiple `@baseline` allowed
- `@decision` SHOULD reference section numbers
- `@consequence` describes the guarantee provided by this artifact
- `@version` aligns with contract version when applicable
- Header is machine-parseable

### 4.2 Test-Level Traceability (Normative)

Contract/integration tests MUST include:

```ts
/**
 * @baseline ADR-0010
 * @verifies Section 3.3
 * @verifies Section 3.4
 */
```

### 4.3 Manifest Generation (Normative)

Each module MUST generate a machine-readable manifest mapping ADRs to implementing files. The manifest is generated automatically (not handwritten).

### 4.4 Reverse Enforcement (Normative)

CI MUST fail if any ADR in `docs/adr/` with `Status: Accepted` has zero implementation references in manifests.

### 4.5 Architecture Graph Generation + Publication (Normative)

The system MUST produce:

- ADR → File mapping
- File → ADR mapping
- ADR → ADR dependency graph (if declared)
- Module-level traceability graph

Outputs:

- JSON (tooling)
- Mermaid export (docs)
- Neo4j ingestion (governance graph)

#### Neo4j requirements

- Publish to Neo4j via idempotent `MERGE`
- Stable keys: `ADR.number`, `File.path`, `Module.name`
- Canonical relationship: `(:File)-[:BASELINED_ON]->(:ADR)`
- `IMPLEMENTED_BY` is a derived query (inverse), not stored.

## 5. Acceptance Criteria

- Header validation exists
- Manifest generator exists
- Reverse ADR coverage validation exists
- CI blocks non-compliant PRs
- Neo4j graph ingestion works and is idempotent
