1. Catálogo parcial (docs generate --select) → OpenLineage ya lo resuelve con facets
Tu diagnóstico: El catalog.json puede ser parcial, y una UI ingenua mostraría "no existe" cuando en realidad el dato sí existe pero no fue seleccionado.

La solución OpenLineage: No depende de catalog.json. El wrapper dbt-ol (o openlineage-dbt) ejecuta dbt docs generate antes de emitir eventos, y extrae los esquemas de columnas del catalog.json generado para los modelos ejecutados . Pero el punto clave: OpenLineage modela los esquemas de columna como un facet del dataset, no como un artefacto separado .

Ejemplo concreto: Cuando ejecutas dbt-ol run, para cada dataset de salida se emite un evento como este, que incluye el facet schema con las columnas reales que ese modelo produjo:

json
{
  "eventType": "COMPLETE",
  "outputs": [{
    "namespace": "snowflake://my_account",
    "name": "analytics.dim_customers",
    "facets": {
      "schema": {
        "_producer": "https://github.com/OpenLineage/OpenLineage/tree/1.0/integration/dbt",
        "_schemaURL": "https://openlineage.io/spec/facets/1-0-0/SchemaDatasetFacet.json",
        "fields": [
          {"name": "customer_id", "type": "NUMBER"},
          {"name": "customer_name", "type": "VARCHAR"},
          {"name": "first_order_date", "type": "DATE"}
        ]
      }
    }
  }]
}
Tu miedo a "falsos negativos" desaparece: Si un modelo no se ejecutó (por --select), no hay evento, no hay dataset en Marquez. Si se ejecutó pero no se generó catalog.json, el facet schema simplemente no aparece, y la UI muestra "sin metadatos de columna" sin ambigüedad. No hay lugar para "no existe" vs "parcial".

2. Identidad: versiones + acceso + contratos → OpenLineage lo maneja con Job versioning
Tu acierto: No puedes usar unique_id directamente, y las versiones de modelos deben ser entidades separadas.

Cómo lo hace OpenLineage: La identidad de un Job en OpenLineage es la tupla (namespace, name) . Para modelos versionados, generas nombres distintos: dim_customers_v1, dim_customers_v2. El wrapper dbt-ol ya hace esto: toma el unique_id de dbt y lo transforma en un nombre de Job estable, pero conservando la versión .

Ejemplo:

Modelo dim_customers versión 1 en dbt → unique_id = "model.my_project.dim_customers.v1"

En OpenLineage: job.name = "my_project.dim_customers_v1", namespace = "dbt" (o tu proyecto/entorno)

Acceso y contratos: Estos se modelan como facets del Job . Puedes tener un facet personalizado dbt_contract_facet que indique si el contrato está forzado, el nivel de acceso, etc. Marquez almacena estos facets y permite consultarlos.

Tu preocupación por "reachability": En OpenLineage, el grafo de linaje se construye a partir de las dependencias reales capturadas en los eventos (inputs/outputs). Si un modelo cambia su acceso (ej: de protected a public), eso no afecta al grafo; afecta a quién puede referenciarlo en futuras compilaciones. Pero ese es un problema de la capa de autoría, no del linaje. Lo capturas en el facet y dejas que la política decida.

3. compiled, compiled_code, relation_name son de run_results → OpenLineage ya los emite en los eventos
Tu crítica: El manifest no tiene estos campos, y el run_results llega después.

La solución probada: El wrapper dbt-ol ejecuta dbt, espera a que termine, y luego:

Lee target/manifest.json

Lee target/run_results.json

Lee target/catalog.json (si existe)

Por cada nodo ejecutado, emite eventos OpenLineage que incluyen en los facets la información relevante .

Ejemplo de facet personalizado para dbt (lo que AWS implementa en su muestra ):

json
{
  "job": {
    "namespace": "dbt",
    "name": "my_project.dim_customers",
    "facets": {
      "dbt_details": {
        "_producer": "...",
        "compiled_code": "SELECT ... FROM ...",
        "relation_name": "analytics.dim_customers",
        "materialization": "table",
        "unique_id": "model.my_project.dim_customers"
      }
    }
  }
}
Tu preocupación por la asincronía: En OpenLineage, los eventos se emiten después de que dbt termina, pero todos juntos. No hay un modelo de "bundle" con artefactos que llegan en diferente orden; hay un único proceso que genera todos los eventos de una invocación. Si usas dbt-ol en modo streaming (con logs estructurados), puedes obtener eventos a medida que cada modelo termina, pero el compiled_code y relation_name solo están disponibles al final. En cualquier caso, el modelo de eventos es inmutable y content-addressed (por runId), así que no hay problema de consistencia.

4. deps_fingerprint y package-lock.yml → OpenLineage lo captura en el contexto del Job
Tu intuición: El grafo cambia si cambian las dependencias, aunque el código del modelo no cambie.

La realidad OpenLineage: Cuando ejecutas dbt-ol run, el wrapper captura el entorno completo de ejecución. No hay un "hash de dependencias" explícito, pero cada evento de Job incluye el contexto (versión de dbt, etc.). Además, Marquez versiona los Jobs: si el mismo nombre de Job aparece con un código diferente (porque cambió el paquete), se crea una nueva versión del Job .

Implementación concreta: El proyecto de AWS  muestra cómo integrar dbt con OpenLineage en un entorno productivo, incluyendo gestión de dependencias. El wrapper dbt-ol ya incluye en los metadatos la información de paquetes disponible en el manifest.

Pero si quieres ser explícito: Puedes extender el wrapper para añadir un facet dbt_dependencies que contenga el hash de package-lock.yml. Eso es lo bueno de OpenLineage: puedes añadir facets personalizados sin romper el estándar .

5. config_fingerprint en plan_hash → OpenLineage lo resuelve con la distinción Job vs Run
Tu diseño: Separar graph_hash (estructura) de exec_hash (configuración de ejecución).

Cómo lo hace OpenLineage: Esta separación es exactamente la distinción entre Job (definición estática) y Run (ejecución concreta) .

Job: representa la definición del modelo (equivalente a tu graph_hash implícito). Tiene facets como sql, sourceCodeLocation, etc. .

Run: representa una ejecución concreta (equivalente a tu exec_hash). Tiene facets como nominalTime, errorMessage, y facets personalizados con configuración específica de esa ejecución .

Ejemplo: El proyecto "Budgets as Code"  muestra exactamente cómo se usan los facets de Run para capturar políticas de ejecución (en su caso, presupuestos). Cada ejecución lleva un facet budget con la decisión de admisión, el Git SHA de la política, etc. .

Tu plan_hash sería simplemente el hash del runId + facets seleccionados.

6. Concurrencia: ON CONFLICT DO NOTHING no basta → OpenLineage + Marquez usan inmutabilidad
Tu propuesta: Separar artifact (inmutable por hash) de bundle (mutable, referencia a artifacts).

La implementación Marquez: Marquez almacena eventos OpenLineage de forma inmutable. Cada evento tiene un runId único y se almacena tal cual. No hay "actualizaciones", solo inserciones. La concurrencia se maneja a nivel de base de datos (PostgreSQL) con transacciones .

Ejemplo de cómo Marquez maneja múltiples runs con el mismo manifest:

Run A: se ingiere, se crea un Job y un Run en Marquez.

Run B: mismo manifest, pero diferente runId. Marquez crea otro Run para el mismo Job (porque el nombre del Job es el mismo). No hay conflicto, porque los Runs son entidades separadas.

Tu modelo de bundle_artifact es equivalente a cómo Marquez almacena eventos: cada evento es un "artifact", y cada run es un "bundle" implícito. La diferencia es que Marquez ya tiene las relaciones y la API para consultarlos.

Solución sobre Marquez
Retención: Programa un job que borre eventos antiguos de Marquez (directamente en PostgreSQL) según política. Por ejemplo, borrar runs con más de 90 días.

Acceso: Marquez tiene un sistema de API keys, pero no RBAC fino. Puedes poner un proxy (como Kong) delante de la API de Marquez que añada autenticación y autorización basada en el namespace.

Auditoría: Cada vez que alguien consulta la API de Marquez (o la UI), el proxy puede registrar el acceso. También puedes loggear quién ejecutó cada run (ya que los eventos de OpenLineage pueden incluir un facet user).

3) Catálogo parcial: sí, tu argumento gana… pero la solución OL es “coverage explícita”

La idea clave que has expuesto es: si no hay schema facet, no hay ambigüedad. Correcto.

Pero en la práctica te interesa distinguir:

“no hay columnas porque no se ejecutó”

“se ejecutó, pero no tenemos metadata de columnas (o es parcial)”

OpenLineage ya modela el schema como facet opcional.
Lo que falta es marcar “coverage”. Eso lo resuelves con dvt_coverage facet (dataset facet u opcionalmente run facet).

Regla UI:

dataset existe pero sin schema facet ⇒ “sin metadata de columnas”

dataset con schema facet + dvt_coverage.partial=true ⇒ “metadata parcial por selector”

(Esto te salva del “DVT+ es basura” que describes.)

4) Asincronía dbt Cloud: tu “bundle” se reemplaza por “Run is the bundle”

Tu crítica a mi bundle era válida para la ingesta por archivos desordenados.

Con OpenLineage, el runId es el pegamento. Cada ejecución produce eventos asociados al mismo runId; Marquez almacena runs separadamente incluso si el job es el mismo. Esto elimina el caso “manifest duplicado rompe correlación”.

Prácticamente:

Run A y Run B pueden tener el mismo job.name (misma definición) y conviven como runs distintos.

Tu “inmutabilidad” ya está en el modelo.
