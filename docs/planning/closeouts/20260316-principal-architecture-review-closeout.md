# Closeout: Principal Architecture Review

## Think-First

### Problem summary

The PR is documentation-only, but CI fails in the setup/install phase before any
docs checks run. The failing job reports
`ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`.

### Root cause

`package.json` pins the root `pnpm.overrides` entry for `@types/node` to
`25.3.5`, while the committed `pnpm-lock.yaml` still resolves that override as
`25.5.0` across multiple importers. The mismatch is tolerated by the local
pnpm 10 install path after regeneration, but the CI workflow runs pnpm `9.15.9`
and rejects the stale lockfile under `--frozen-lockfile`.

### Constraints and invariants

- Repository CI is authoritative; do not bypass `--frozen-lockfile`.
- This slice must remain docs-only plus the minimal lockfile repair needed to
  make CI truthful.
- No package version policy change is intended here; the fix is lockfile sync,
  not dependency drift.

### Options considered

- Regenerate `pnpm-lock.yaml` with local pnpm 10 and commit it.
  Rejected: it does not match the CI runtime and is what allowed the mismatch
  to survive.
- Change the workflow to pnpm 10.
  Rejected: larger operational change unrelated to this PR.
- Regenerate `pnpm-lock.yaml` with pnpm `9.15.9`, matching CI.
  Selected: minimal, reproducible, and aligned with the failing job definition.

### Selected option and rationale

Regenerate and commit `pnpm-lock.yaml` using pnpm `9.15.9`, then validate with
`pnpm install --frozen-lockfile` under the same pnpm version in a clean
worktree.

### Rejected alternatives

- Bypass the failing workflow.
- Ignore the failure as a stale run.
- Commit a lockfile regenerated by a different pnpm major than CI.
